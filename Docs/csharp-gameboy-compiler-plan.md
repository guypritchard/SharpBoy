# Plan

Build a compiler, hosted on .NET on the development PC, that translates a restricted C# program into a native Game Boy ROM. Use Roslyn for parsing and semantic analysis, a small typed intermediate representation (IR), and RGBDS for assembly, linking and cartridge header generation. The cartridge contains native SM83 instructions, data and a small support library; it contains no CLR, IL interpreter, garbage collector or .NET framework library.

## Scope

- In: original monochrome Game Boy (DMG), 32 KiB ROM-only cartridges, static memory allocation, direct method calls, a documented C# subset, hardware intrinsics, compiler diagnostics, and executable ROM tests in SharpBoy.
- Out initially: compiling arbitrary .NET assemblies, an IL frontend, GBDK/C translation, managed heap allocation, reference-type instances, virtual dispatch, interfaces, delegates, boxing, reflection, exceptions, generics, strings, async, LINQ, recursion, user interrupt handlers, cartridge banking, cartridge saves and Game Boy Color features. Static classes are permitted as containers.
- Delivery boundary: first prove arithmetic, calls and RAM writes in a valid ROM; then deliver a visible scrolling-background demo. Arrays, structs and richer hardware APIs are later extensions rather than prerequisites for the first ROM.

## What remains to implement

Milestones **1-9 are complete**. The compiler currently builds and independently validates native DMG ROMs, including backgrounds, direct-OAM sprites and MBC1 banked read-only assets. The remaining work is optional milestone-10 expansion rather than a blocker for the existing compiler and demos.

### Concrete feature backlog

- [ ] **Input API.** Add deterministic joypad polling for `$FF00`, SDK intrinsics, button-edge semantics, a playable sample, and SharpBoy/PyBoy coverage.
- [ ] **Fixed-size buffers and arrays.** Define allocation, initialization, indexing and bounds behavior. Ordinary C# arrays must not be accepted until their managed semantics are either preserved or explicitly rejected; the MBC1 `$D000-$D7FF` staging area is not a managed array.
- [ ] **Blittable structs.** Define field ordering, padding/alignment, copying, nested layout, initialization and ABI passing rules before accepting user structs.
- [ ] **Additional arithmetic.** Implement and test multiplication, division and remainder (including signed edge cases and divide-by-zero behavior). Checked arithmetic remains unsupported until a target failure contract exists.
- [ ] **Shadow OAM and DMA.** Add a 160-byte shadow-OAM model and an HRAM-safe DMA routine. First improve SharpBoy's DMA timing, CPU bus blocking and HRAM-only execution model so tests do not validate an instantaneous-emulator shortcut.
- [ ] **Interrupts and interrupt-safe storage.** Define IME ownership, vector handlers, register preservation, nested/reentrant state and interaction with bank switching. Current generated ROMs intentionally keep interrupts disabled.
- [ ] **General function ROM banking.** Add deterministic function placement, ROM0 far-call trampolines, nested bank save/restore, cross-bank return values and stack accounting. Current MBC1 support banks read-only assets only; executable code remains in ROM0.
- [ ] **Cartridge RAM and saves.** Add mapper-specific RAM enable/banking, persistent save format and initialization semantics. Current MBC1 cartridges declare no external RAM.
- [ ] **Larger/other cartridges.** Support MBC1 upper-bank bits beyond the current 32-bank limit and, only with separate designs/tests, other mappers or Game Boy Color targets.
- [ ] **Optimizations.** Add only semantics-preserving IR passes with differential ROM tests; the current spill-heavy backend favors correctness and inspectability.
- [ ] **Source-level debugger integration.** Consume generated source locations and `.sym`/`.map` data for source breakpoints, stepping and variable inspection. Artifacts exist, but `GB.Debugger` does not yet provide C#-level debugging.
- [ ] **Optional IL frontend.** Consider this only after the source frontend, IR and ABI are stable; it must enforce exactly the same target restrictions and must not imply CLR support.

### Validation still outside the implementation proof

- [ ] Run the new GitHub Actions workflow on the hosted runner and exercise release publication; only the equivalent local workflow has been verified so far.
- [ ] Validate representative ROMs on physical DMG hardware and, if desired, with an authentic boot ROM. Existing automated execution deliberately starts at `$0100` in SharpBoy and PyBoy and does not prove analog display, cartridge electrical or cycle-exact hardware behavior.

Recommended next order: **input**, then **fixed-size buffers/structs**, then an accurate **DMA model**, followed by **function banking/save RAM**. Each item remains independently scoped and must update the language/ABI documents and add real-ROM tests before its checkbox is marked.

## Open questions


- Should the first release ship as a standalone CLI or a local .NET tool? Default: a CLI with explicit source inputs; MSBuild integration follows later.
- Which independent emulator and version should be the reference validator? **Resolved for milestone 8:** PyBoy 2.6.0, synthetic boot unmapped and PC set to `$0100`; see [validation](csharp-gameboy-independent-validation.md).
- Should the compiler eventually accept general C# array syntax or offer dedicated static-buffer APIs? Defer until after the scrolling demo; do not block the initial compiler on this decision.
